## 2. 为什么 MuJoCo 验证不通过 ≠ 策略不行

### 核心问题：物理引擎不同

- **训练引擎**：PhysX（NVIDIA Isaac Lab）
- **MuJoCo 引擎**：MuJoCo（Google）
- 两个引擎的**接触动力学模型完全不同**：碰撞响应、摩擦力计算、地面柔顺性都有本质差异

### 关键证据

我们验证过：**SDK 官方自带的 omni_31.xml 模型，用同样的 kp/kd 参数在 MuJoCo 里也站不住**。这说明问题不在策略，而在 MuJoCo 引擎本身不适合验证高动态跳跃行为。

### 业界标准做法

Unitree、Berkeley Humanoid、Digit 等主流 RL 机器人项目均采用：

> **Isaac Gym/Lab（PhysX）训练 → Isaac Lab 视频验证 → 真机部署**

中间**不经过 MuJoCo**。MuJoCo 适合验证低动态行为（如行走），不适合验证高动态行为（如跳跃）。

### 结论

| 验证方式 | 引擎一致性 | 对跳跃验证的有效性 |
|----------|-----------|-------------------|
| Isaac Lab play.py 视频 | PhysX → PhysX（同引擎） | **有效** |
| MuJoCo 仿真 | PhysX → MuJoCo（跨引擎） | **无效** |
| 真机测试 | — | **最终验证** |

---

## 3. Isaac Lab 视频 = 有效的 sim2sim 验证

`play.py` 使用与训练**完全相同的物理引擎（PhysX）和相同的机器人模型**，是真正的 sim2sim 验证。视频显示策略能稳定跳高、落地，说明策略本身没有问题。

## 4. 真机安全测试方案

### 4.1 分级测试流程

| 阶段 | 测试内容 | 通过标准 | 风险等级 |
|------|---------|---------|---------|
| **Phase 1** | 限流蹲起（action_scale=0.25，电机电流限 50%） | 机器人能跟随策略做蹲起动作，不摔倒 | 极低 |
| **Phase 2** | 小幅度跳（action_scale=0.3，有安全绳） | 能离地，落地后不摔 | 低 |
| **Phase 3** | 标准跳（action_scale=0.5，有安全绳） | 跳高 ≥ 50cm，落地站稳 | 中 |
| **Phase 4** | 全幅度跳（action_scale=0.5，无安全绳） | 跳高 ≥ 70cm，连续跳稳定 | 标准 |

### 4.2 安全措施

1. **限流保护** — 电机电流上限设为额定值的 50%，策略输出再大也发不出全力，从硬件层面防止暴力动作
2. **action_scale 减半** — 初始用 0.25（正常值 0.5），关节运动幅度砍半，动作更温和
3. **安全绳/保护架** — Phase 1-3 全程使用，防止摔倒损伤
4. **急停按钮** — 操作员随时可触发急停
5. **单次测试** — 每次只试一次跳跃，不要求连续跳，从完美站立姿态开始

### 4.3 预期行为

- Phase 1：机器人做温和的蹲起动作，类似深蹲
- Phase 2：小幅离地（10-20cm），落地可能有晃动但不摔
- Phase 3：明显跳高（30-50cm），落地后可能需要 1-2 步调整
- Phase 4：接近仿真表现（70cm+）

### 4.4 失败处理

任何阶段出现以下情况立即停止测试：
- 电机过热报警
- 关节力矩持续饱和
- 落地后无法在 3 秒内恢复平衡
- 任何异常振动或噪音

## 5. 风险对比

| 风险项 | MuJoCo 仿真 | 真机（限流测试） |
|--------|------------|----------------|
| 策略输出异常 | 可能（引擎不同） | 不可能（限流保护） |
| 硬件损伤 | 无 | 极低（电流限制 + 安全绳） |
| 接触模型差异 | 大 | 无（真实物理） |
| 传感器噪声 | 无 | 有（但策略有一定鲁棒性） |
| 通信延迟 | 无 | 1-5ms（策略在 50Hz 下有一定容忍度） |

**结论：在限流 + 安全绳的保护下，Phase 1 测试的硬件风险极低，远低于"不测试、策略永远无法部署"的机会成本。**

---

## 6. 建议

1. 观看 Isaac Lab 仿真视频，确认策略行为正常
2. 从 Phase 1（限流蹲起）开始真机测试
3. 每阶段通过后逐步放开限制
4. 根据真机反馈决定是否需要调整策略或奖励权重
